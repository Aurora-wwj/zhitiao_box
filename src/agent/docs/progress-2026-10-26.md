## 1. 当前结论

当前阶段为“AI/API、真实编译烧录的软件封装，以及人工审批的软件模拟反馈闭环已实现；真实硬件闭环等待部署回归和观测接口”。不能表述为四个真实接口已经全部验收，或 AI 已能自动修复真实开发板。

本轮新增 Orchestrator、Agent.decide、SourceEditor、FeedbackMockBackend、ObservationBackend 和 agent-demo 入口。已在隔离测试中验证：模拟周期 800 ms → 模型提出源码修改 → 展示 diff → 人工批准 → 修改临时源码 → 重新模拟构建/烧录 → 周期 1001 ms → PASS。

默认演示的“模型”是确定性的脚本替身，工具也是模拟；没有 Keil 编译或 FPGA 物理测量。可显式使用 NiceCode 生成真实 AI 决策，但硬件工具仍为 mock，源码仍仅为演示新建的临时文件。

最近云端 Linux / Python 3.13.5 的 140 项测试全部通过。用户曾提供 Windows 上早期 59 项测试通过及 NiceCode 建议调用成功的记录；新版 140 项测试和真实后端的部署 PC 回归仍待确认。

## 3. 当前入口和可以演示的内容

| 入口 | 行为 | 是否联网/修改文件 |
| --- | --- | --- |
| mock | 运行原有固定模拟流程 | 不联网、不编译、不烧录 |
| suggest | 调用 NiceCode 获取建议 | 显式允许联网后可能计费；不应用建议 |
| agent-demo | 800 ms → 待审 diff → 批准后修改 → 1001 ms 的模拟循环 | 默认离线脚本模型；只在批准后修改临时源码 |
| agent-demo 加 allow-network/protocol | 同一模拟循环，由 NiceCode 提供决策 | 可能计费；只发送临时演示源码及模拟证据，不读取当前仓库 |
| real-build | 预览 Keil 计划，人工批准后编译 | 实际运行部署 PC 的 Keil，写构建产物及日志 |
| real-flash | 预览上传和烧录计划，人工批准后执行 | 实际连接 Zynq 并烧录；需非交互认证及可信主机密钥 |

Orchestrator 根据 Controller.max_attempts 限制为最多 1–3 轮，时间预算包含等待人工批准。待审状态下再次推进不会重复执行工具或请求模型；拒绝、输入变化、超时和终态会停止。

一次只审一个文件的完整替换 diff。文件必须是明确白名单中的现有 C/C++/头文件/汇编文件；拒绝绝对路径、父目录穿越、符号链接及 Git/Agent 元数据。单个 UTF-8 文件最多 128 KiB，上下文最多 8 个文件、合计 256 KiB。

这些是确定性软件约束，不是操作系统沙箱，也不能代替对源码语义的人工审阅。GBK 工程、跨进程恢复和多文件事务编辑尚不支持。

## 5. 最终软件分层与当前差距

最终结构：用户目标 → Agent/Orchestrator → Controller 安全边界 → 四个工具 → 日志与物理测量反馈 → Agent 分析并提出源码 diff → 人工批准 → 应用修改 → 新一轮验证。

- Agent：理解任务上下文、分析证据、提出修改或停止，不能自行批准、执行命令或声明通过。
- Controller：固定路径范围、执行顺序、最大次数、审批和确定性判定。编译失败不烧录，未校验不进入后续测试。
- HardwareBackend：负责 Keil、SSH/SCP、OpenOCD、UART 和 PL 的具体访问，不向模型暴露任意底层命令。
- SourceEditor：绑定版本摘要，展示 diff，在批准仍有效时修改明确授权的源码。

该分层已通过软件模拟场景连接起来；当前目标仍为显式配置的 GPIO 周期参数，不是任意自然语言硬件目标的通用解析器。

将这一结构连接到真实工程和板端，需要继续完成真实观测访问、逐步审批状态机、工程上下文管理及实机故障处理。不能通过把 RealBackend.requires_approval 改成 false 来绕过。

## 7. 人员、电脑与硬件协作

| 角色/位置 | 下一步负责事项 |
| --- | --- |
| AI 开发电脑 | 运行新测试和模拟闭环；可选用 NiceCode 验证结构化决策；不要求安装 Keil 或连接板卡 |
| 硬件部署 Windows PC | 保存项目和 STM32 工程、安装 Python/Keil、连接 Zynq；配置 deployment.local.json 并回归真实 build/flash |
| 硬件队友 | 配置板端 key 登录、核对主机指纹、验证实际 GPIO 行为、提供 UART/PL 的访问定义 |
| 双方共同 | 对齐日志时间戳、GPIO 完整周期单位、容差、错误码、审批边界，保存脱敏成功与失败记录 |

UART 适配约定：uart_reader(duration_s, timeout_s) 返回按时间排序的 timestamp_ms/text 列表。PL 适配约定：period_reader(timeout_s) 返回 period_ms，程序自行计算 passed。接口不是设备驱动；不能用固定值或 STM32 自报数据冒充 FPGA 实测。

当前实机仍由队友手动输入 SSH 密码。非交互认证是目标要求，代码已支持并不意味着部署完成；程序不会自动给开发板配置公钥。密码、私钥正文和 API Key 不写入仓库。

## 8. 路径和结果约定

| 项目 | 约定 |
| --- | --- |
| SD 根目录 | /sd |
| OpenOCD | /sd/tools/openocd/bin/openocd |
| scripts | /sd/tools/openocd/share/openocd/scripts |
| 固件目录 | /sd/firmware/<run_id>/firmware.hex |
| 日志根目录 | /sd/logs |
| 启动文件保护 | 不在普通固件流程中覆盖 BOOT.BIN、image.ub |
| 上传完整性 | artifact_sha256 与 remote_sha256 相同后 upload_verified=true |
| 烧录成功 | 正常退出并确认 Programming Finished、Verified OK、Resetting Target 后 verified=true |
| 工具与物理行为 | success 表示工具工作正常，passed 表示测量满足目标，二者不混淆 |
| GPIO 示例 | 完整周期 1000 ms，误差不超过 50 ms，不是单次翻转间隔 |

部署参考为 PC Ethernet 192.168.10.1/24、Zynq 192.168.10.2、SSH 用户 root、端口 22。实际 Keil 和工程路径以部署电脑为准；Python 配置不会自动更改网卡、固定开机 IP 或建立免交互认证。

上传流程为本地 HEX/SHA-256 → SCP → 远端大小检查 → 远端 SHA-256 → 一致后 OpenOCD。大小不符、摘要不符、计算失败或解析失败均停止，不退回只检查大小。SSH 超时后仍需人工检查远端是否有残留进程，不自动重复烧录。

## 9. 当前复现与演示命令

在项目根目录的 Windows PowerShell 运行：

```powershell
git pull --ff-only origin main
$env:PYTHONPATH = "src"
py -3.13 -B -m unittest discover -s tests -v
py -3.13 -B -m zhidiao_agent mock
py -3.13 -B -m zhidiao_agent agent-demo
```

预期为 140 项测试通过、原 mock 返回 PASS。agent-demo 显示 diff 后等待人工输入 APPROVE 加完整 fingerprint；正确批准后下一轮模拟达到 PASS。非交互环境停在 AWAITING_APPROVAL 并返回退出码 1，不应用修改。

仅在已安全配置 NiceCode 环境变量且允许真实调用时，使用：

```powershell
py -3.13 -B -m zhidiao_agent agent-demo --protocol openai-responses --allow-network
```

该模式可能计费，仍只使用临时模拟工程和模拟工具。真实模型不保证给出固定 1001 数值；只要确定性测量满足目标才 PASS。

在硬件部署 PC 按 v0.3 接线手册配置 deployment.local.json，先 real-build --preview-only，核对后单项批准，再准备认证并单项预览/批准 real-flash。已有本地配置保留，不用队友的盘符覆盖自己的实际路径。

详细说明：docs/orchestrator.md（软件闭环）与 docs/integration-v0.3.md（真实编译/烧录）。
