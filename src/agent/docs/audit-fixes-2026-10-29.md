# 文件核查后的三项修复

依据 v0.5 规划和用户实测反馈，代码继续发布到 main。四个硬件接口及 contract_version=0.2 保持不变。

## 1. 真实目标与部署能力绑定

原生 PLPeriodReader 新增纯配置校验，真实 UI、CLI、Controller 预览和实际观测都会检查。

目标周期加容差的上界必须同时满足：

```text
计数上限 = (2^32 - 1) / pl_clock_hz * 1000 ms
窗口上限 = (observation_timeout_s - poll_interval_s) * 1000 / (min_new_edges + 1)
允许上界 = min(计数上限, 窗口上限)
```

额外一个完整周期用于初始相位及一致性读取余量。默认窗口 15 秒、轮询 0.05 秒、至少 2 个新边沿时，周期与容差上界约为 4983.333 ms，当前 1000±50 ms 任务仍可用；60 秒目标会在批准、构建和烧录之前被拒绝。程序不会自行扩大窗口或改变验收目标。

范围只表示满足配置的必要条件，不保证缺失、错误或过慢的真实信号一定能采集到。运行中剩余预算不足时返回 TIMEOUT。模拟模式独立使用其虚拟周期范围，不套用真实计数器和采样窗口；自定义观测回调须自行声明、约束对应能力。

## 2. 首次模型请求前开始持久化

TaskAudit 在首次模型请求前分配 run_id，并写入 .zhidiao/runs/。记录任务、所选源码 SHA、模型配置、目标响应、补充问答、审批身份／参数及错误码；不保存认证配置或原始 HTTP 头。

- UI 需先有上下文发送同意；CLI 的同意与拒绝也记录在本地审计中，拒绝不触发模型请求。
- API 超时、HTTP 服务错误、无效目标响应、目标不支持、严格模式目标拒绝均可查到 task_entry 报告。
- 目标解析中标记 in_flight=goal_interpretation；结束或失败时清除。
- 开始执行后沿用同一 run_id，执行报告替换同名任务入口报告，保留 task_entry 上下文。
- report_stage=task_entry 的报告为只读证据，不能恢复执行。旧权限不从报告恢复。
- 后续无效请求不会覆盖已经完成报告的原始失败原因。
- 首次归档失败时停止模型请求；执行后归档失败会返回错误，并保留返回结果中的已有工具证据，不伪装为“尚未执行”。磁盘不可写或进程被强杀时不能保证文件已落盘。

报告只在 PC 持久化。本轮未增加 /sd/logs/ 归档、清理或冷启动配置。

## 3. 模型来源字段统一

真实 UI、真实 CLI、模拟硬件 UI 和直接 Orchestrator 均使用 provenance.py 生成字段：

```json
{"source":"nicecode_api","requested_model":"gpt-5.6-sol","protocol":"openai-responses"}
```

字段记录配置的请求模型和协议，不认证第三方实际运行的模型权重。脚本模式标为 scripted；未报告身份的自定义客户端标为 custom；尚未构造客户端时为 uninitialized。不猜测自定义回调的模型名，不导出 API Key、授权头或客户端 repr。

模型元数据进入恢复绑定。未包含兼容模型信息的旧执行检查点仍可查看，但可能需要开新任务，不能强行沿用旧授权。
