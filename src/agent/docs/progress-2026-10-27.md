# 智调盒 Agent 项目进度与后续工作计划

更新日期：2026 年 10 月 27 日，v0.4 审查遗漏补全版。

仓库：https://github.com/Aurora-wwj/zhidiao-agent

本文区分硬件队友已验证的三接口、本轮软件修复与新功能，以及仍需部署验收的部分。旧阶段的测试数和 PDF 快照不代表本轮最终验证结果。

## 1. 当前结论

硬件队友已在部署 PC 和板卡上验证 build_firmware、flash_firmware、run_hardware_test 三个真实接口，并完成当前运行环境中的非交互 SSH key 认证。实际测量对象是接线到 PL 的 STM32 PA1，约 601 ms；对 1000±50 ms 返回 FAIL，对 600±50 ms 返回 PASS。

本轮修复“复用后端切换配置后可能读取旧板”的问题，补上 PA1 身份校验，并补齐浏览器按钮操作、连续目标澄清、部署配置向导、受审批的 PL 内部加载、持久化报告与安全检查点恢复。四个公开工具接口保持稳定。

真实 UART reader 仍待硬件访问契约。新版允许显式 PL-only 模式；它的 PASS 只覆盖已配置物理引脚的周期目标。队友此前实机通过三接口，不等于本次新增整链已完成实机回归。

## 3. 本轮修复的两个遗漏

之前同一个 RealBackend 被赋予新部署配置后，原生 PLPeriodReader 可能仍保留旧地址，导致构建/烧录操作新板而测量旧板。本轮将后端绑定到初始部署：配置改变、原生 reader 配置或 transport 不匹配时拒绝预览和执行；切换板卡要新建后端并重新批准。

v0.4 PDF 的实测对象是 PA1。现在 observer.observed_gpio 明确记录该物理通道，用户明确指定其他引脚时在模型请求前拒绝，模型 ready 结果也必须匹配。目标确认、真实轮次预览和报告显示同一引脚，避免把 PA1 的结果用于其他 GPIO。

## 4. PL 生命周期与部署向导

默认 check_only 读取已由部署方准备的 measurement-v3，检查 prog_done 和可选 SD 文件 SHA。load_verified 模式要求显式 .bit 路径和 SHA-256，审批明确展示替换 FPGA 的效果；批准后才校验并加载 /dev/xdevcfg，再检查 prog_done，每轮在 UART/PL 前准备一次。

运行时加载是 PDF 的内部准备方案 B，可在 SSH 可用时恢复 PL，不需要增加第五个公开工具。它不写 BOOT.BIN、image.ub 或启动脚本。prog_done 只证明配置完成，SD 文件 SHA 只证明文件完整，不能把两者当作当前运行镜像的硬件身份认证。

| 已知部署事实 | 当前处理 |
| --- | --- |
| STM32 工程 | E:\Project\GPIO_PL_Test，按本机路径配置 |
| 实际观测引脚 | STM32 PA1 → PL input |
| Zynq | root@192.168.10.2:22；SSH HOME 为 /home/root |
| PL 时钟 | 100 MHz |
| period / high | 0x43C30000 / 0x43C30008 |
| edge / valid | 0x43C40000 / 0x43C40008 |
| 镜像 | zhidiao_measure_v3.bit，SHA 见部署手册 |
| prog_done 路径 | 示例是候选值，须由队友确认实际节点 |
| 旧版 Dropbear | 保持受控 ssh-rsa 与 legacy SCP 兼容 |
| 非交互工具 | /bin/busybox 等明确路径，避免依赖交互 PATH |

新增 deployment-setup 生成经审阅的本地配置；已有文件不覆盖。deployment-check 只读检查 SSH、实际 HOME、authorized_keys、OpenOCD/scripts、ST-Link USB 候选和 PL 访问条件。诊断出现 FAIL/UNKNOWN 时明确返回未就绪/不完整；它不能代替 SWD、镜像身份、新边沿或烧录验收。

## 5. 用户层与审计恢复

终端 agent-run 和本机浏览器 serve 都展示固定源码白名单和 PA1。用户同意模型发送范围后，模型提取完整周期和容差；缺失信息可继续回答，最多补充三轮。初始目标解析、等待确认和后续轮次都计入总预算。

每轮真实验证与每次源码修改分别审批。load_verified 的 PL 加载效果在真实验证计划中展示。LLM 只提出 edit/stop，PASS 仍由 abs(measured_period_ms - expected_period_ms) <= tolerance_ms 计算。

报告默认位于 .zhidiao/runs，以 run_id 关联源码/固件摘要、工具结果、模型决策、批准预览与状态；采用原子 JSON 保存，可重开查看或下载。恢复核对相同任务、目标、部署、白名单、源码和限制，保留已用次数与时间（含停机时间），创建新 run_id 与 parent_run_id。

旧批准永不恢复；待编辑和待执行均重新预览/审批。报告标记为执行中时拒绝自动继续，先检查硬件再开始新的已审阅运行。终态报告可查看而不追加执行。

## 6. 验证证据

本轮 Python 3.13 Linux 软件测试：310 项全部通过；mock CLI、离线示例、浏览器脚本语法检查通过。测试覆盖旧板卡错读回归、错误引脚拒绝、PL 加载审批、部署向导、浏览器请求与安全恢复。原生 Windows 与板卡验收仍须在部署环境完成。

测试使用 mock 模型、传输和硬件 runner，并执行基于模拟 BusyBox/寄存器/加载设备的 helper；不要求在线 NiceCode、真实密钥或开发板。软件测试不能证明原生 Zynq BusyBox、新版 Windows CI 或真实 AI 修复闭环已经通过。

队友 v0.4 的实机证据继续有效：基础 build、flash、PL 真测和非交互 SSH 已验证。本轮的新后端身份、PA1 绑定、PL 加载、GUI 和恢复流程还需在部署环境回归。

## 8. 推荐本地步骤

在仓库根目录 PowerShell：

```powershell
$env:PYTHONPATH = (Resolve-Path ".\src").Path
py -3.13 -B -m unittest discover -s tests -v
py -3.13 -B -m zhidiao_agent agent-demo
```

先检查模拟拒绝不写入、批准后 PASS。部署 PC 再核对 profile、PA1 接线、known_hosts、身份密钥和 measurement-v3，预览 deployment-check、real-build、real-flash 和 real-test。

三接口回归后使用 agent-run 或 serve，并显式 --pl-only；需要加载 PL 时先核对镜像和 SHA，再选择 load_verified 并审阅该效果。UART 到位后移除 --pl-only，验收四接口。命令见 [v0.4 手册](integration-v0.4.md)，恢复与模型边界见 [Orchestrator 说明](orchestrator.md)。

## 9. 当前限制

一次只修改一个现有白名单 UTF-8 文件，单文件最多 128 KiB，模型上下文最多 8 文件、合计 256 KiB。无任意 shell、自动提交/推送或模型自批准入口。保存报告不等于持久化授权；这些软件边界也不能替代操作系统隔离或保证已批准 C 代码正确。

SSH 中断不能保证远端 OpenOCD 已结束。烧录上传已核对后发生超时／取消／连接中断，或内部 FPGA 加载可能被中断时，报告保留 hardware_state_uncertain 标记。自定义模型/reader 回调须遵守 I/O 截止时间；故障恢复先确认设备状态，不自动重复执行未知结果的操作。部署向导不安装公钥、不修改启动文件，真实 UART 和冷启动持久化仍待硬件侧完成。
